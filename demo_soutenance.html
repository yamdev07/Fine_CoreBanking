🎬 Les 8 étapes — clique pour marquer comme faite
1
Connexion — Authentification JWT
Ouvrir localhost:3000 → Saisir testuser01 / Test1234! → Se connecter
🟣 Avant de cliquer — intro à dire au jury
"Je vais commencer par ce qui est fondamental dans une architecture Zero Trust : l'identité. Ici, aucune confiance implicite — chaque utilisateur, chaque requête, doit prouver qui il est avant d'accéder à la moindre ressource. Je me connecte avec le compte d'un comptable."
🔵 Pendant la connexion
"Je saisis le nom d'utilisateur et le mot de passe. Le mot de passe est haché en base avec bcrypt — même moi, en tant que développeur, je ne peux pas lire le mot de passe réel en base de données."
🟢 Quand le tableau de bord apparaît
"La connexion a réussi. Ce que le système vient de faire en coulisse, c'est générer un token JWT — un JSON Web Token signé en HS256 avec une clé secrète. Ce token encode l'identité de l'utilisateur, son rôle ACCOUNTANT, et une date d'expiration de 30 minutes. À partir de maintenant, chaque requête vers l'API transporte ce token en en-tête. Le serveur n'a aucune session à maintenir — il vérifie uniquement la signature cryptographique à chaque appel. C'est l'architecture stateless qui permet la scalabilité horizontale tout en garantissant la sécurité."
2
Écriture déséquilibrée → rejetée 422
Aller dans Écritures → Nouvelle écriture
Ligne 1 : Compte 571100, Débit 100 000, Crédit 0
Ligne 2 : Compte 251100, Débit 0, Crédit 50 000
→ Enregistrer → erreur rouge
🟣 Avant de saisir
"Je vais maintenant vous montrer la première règle fondamentale de la comptabilité en partie double, qui est aussi la première ligne de défense contre la fraude et les erreurs : le principe d'équilibre. Je vais volontairement créer une écriture incorrecte pour voir comment le système réagit."
🔵 Pendant la saisie
"Je crédite le compte 571100 — c'est la Caisse — de 100 000 francs CFA. Et je mets en face le compte 251100 — Crédits court terme — mais seulement 50 000 francs. Il me manque 50 000 francs. Ce type d'erreur, dans un système bancaire réel, pourrait signifier un détournement ou une simple faute de saisie — dans les deux cas, le système ne doit pas l'accepter."
🟢 Quand l'erreur s'affiche
"Rejeté. La validation est double : d'abord Pydantic au niveau de l'API FastAPI vérifie que la somme des débits est strictement égale à la somme des crédits — c'est une validation métier. Ensuite, une contrainte CHECK en PostgreSQL empêche même une insertion directe en base si quelqu'un contournait l'API. Les comptes utilisés ici sont ceux du Plan Comptable des Établissements de Crédit — le PCEC de la BCEAO. Ce n'est pas un plan de comptes inventé : c'est le référentiel officiel des banques en zone UEMOA."
3
Écriture équilibrée → acceptée DRAFT
Corriger Ligne 2 → Crédit 100 000 → Enregistrer
🟣 Avant de corriger
"Je corrige l'écriture — les deux lignes sont maintenant équilibrées. Débit 100 000, Crédit 100 000. Je soumets."
🟢 Quand DRAFT apparaît
"L'écriture est créée avec le statut DRAFT — brouillon. Elle a un numéro de séquence unique, horodatée à la seconde. Elle existe dans le système, mais elle n'a pas encore d'impact sur les soldes des comptes, ni sur les états financiers. C'est le cycle de vie que j'ai implémenté : DRAFT → POSTED → REVERSED. Ce workflow à trois états permet à un comptable de préparer ses écritures, de les vérifier, puis de les valider en toute conscience. C'est une pratique recommandée par les référentiels SYSCOHADA."
4
Validation → POSTED — le principe WORM commence POSTED
Sur l'écriture DRAFT → cliquer Valider / Poster
🟣 Avant de valider
"Maintenant je valide l'écriture. C'est l'action irréversible. Je veux attirer votre attention sur ce moment — parce que c'est là qu'un des principes de sécurité les plus importants de ce système entre en jeu."
🔵 En cliquant
"Je clique sur Valider."
🟢 Quand le badge POSTED apparaît
"L'écriture est maintenant POSTED. À cet instant, le principe WORM entre en vigueur — Write Once, Read Many. L'écriture peut être lue autant de fois qu'on veut, mais elle ne peut plus être modifiée, ni supprimée. Ce n'est pas un simple flag en base de données qu'on pourrait changer — chaque endpoint de l'API vérifie le statut avant toute opération d'écriture, et renvoie une erreur si l'écriture est déjà validée. C'est une réponse directe au threat STRIDE catégorie 'Tampering' — falsification des données comptables — qui est l'un des risques les plus graves dans un système bancaire."
5
WORM — l'écriture validée est intouchable 422
Phase 1 — dans l'interface : Regarder l'écriture Validée → constater que le bouton Valider a disparu, remplacé uniquement par Extourner

Phase 2 — prouver que c'est l'API qui bloque :
Ouvrir localhost:8000/docs
① POST /api/v1/auth/login → Try it out → testuser01 / Test1234! → Execute → copier access_token
② Bouton 🔒 Authorize en haut → coller le token → Authorize → Close
③ GET /api/v1/journal-entries/ → Try it out → Execute → copier le champ "id" (UUID) d'une écriture "status": "POSTED"
④ POST /api/v1/journal-entries/{entry_id}/post → Try it out → coller cet UUID → Execute
→ Réponse : 422 — "Écriture déjà validée / immuable"
🟣 En montrant l'interface
"Regardez ce qui s'est passé dans l'interface : le bouton Valider a simplement disparu. Il n'est plus là. L'interface reflète l'état réel du système — une écriture validée ne peut plus être re-validée. Mais je veux aller plus loin et vous prouver que ce n'est pas juste un bouton caché dans le frontend. Je vais appeler l'API directement."
🔵 En ouvrant Swagger
"Voici la documentation interactive de l'API — Swagger UI, générée automatiquement par FastAPI. N'importe qui avec accès réseau peut appeler ces endpoints directement, sans passer par l'interface. Je prends l'ID de l'écriture que je viens de valider, et je tente de la valider à nouveau via l'API brute."
🟢 Quand le 422 s'affiche dans Swagger
"422 — refusé. Même en attaquant l'API directement, sans passer par l'interface, la réponse est identique. Ce refus n'est pas cosmétique — il vient d'une vérification dans le code métier côté serveur : si le statut de l'écriture est POSTED ou REVERSED, toute tentative de modification est immédiatement rejetée. C'est ce qu'on appelle la non-répudiation : personne ne peut nier avoir passé une écriture, et personne — ni l'utilisateur, ni un administrateur, ni un accès direct à l'API — ne peut la modifier après coup. C'est la réponse au threat STRIDE catégorie 'Tampering'."

🟢 Après le 403 dans Swagger

Le serveur vérifie le rôle dans le token JWT avant d'exécuter la moindre logique métier. C'est la défense en profondeur : deux couches indépendantes — l'interface qui cache, l'API qui refuse. Supprimer l'une ne compromet pas l'autre. C'est la réponse au threat STRIDE 'Elevation of Privilege'."

"Je vais maintenant vous montrer le deuxième service de cette architecture — le service de Reporting. C'est un microservice complètement séparé, qui tourne sur un port différent et qui n'a accès à la base de données qu'en lecture. Je voulais que cette isolation soit architecturale, pas juste une convention."
🔵 Pendant l'affichage des états
"Voici la balance générale — elle reprend tous les comptes avec leurs soldes débiteurs et créditeurs. Et ici le bilan comptable, avec l'actif d'un côté et le passif de l'autre."
🟢 Quand les états s'affichent
"Ces états sont produits conformément au PCIMF — Plan Comptable des Institutions de Microfinance — et au PCEC de la BCEAO. Ce ne sont pas des formats que j'ai inventés : ce sont les plans de comptes réglementaires applicables aux établissements financiers en zone UEMOA. Le service Reporting consomme les événements publiés par Kafka depuis le service Comptabilité — il ne fait jamais d'appel synchrone. En cas de panne du Reporting, la Comptabilité continue de fonctionner. C'est le couplage faible, un des principes clés de l'architecture microservices."
8
Extourne — correction réglementaire SYSCOHADA REVERSED
Se reconnecter testuser01 / Test1234! → Sur l'écriture POSTED → cliquer Extourner
🟣 Avant de cliquer Extourner
"Je reviens en comptable. Je vais vous montrer la dernière fonctionnalité — et c'est celle qui illustre le mieux la contrainte réglementaire SYSCOHADA. J'ai une écriture validée qui contient une erreur. Je ne peux pas la modifier — on l'a vu à l'étape précédente. Alors, comment la corriger sans violer le principe d'immuabilité ?"
🔵 En cliquant Extourner
"En SYSCOHADA, la seule correction autorisée d'une écriture validée, c'est l'extourne. Je clique sur Extourner."
🟢 Ce que tu vois à l'écran — l'originale passe en 'Extournée', une nouvelle EX apparaît en 'Validée'
"Deux choses se passent simultanément. L'écriture originale change de badge : elle passe de 'Validée' à 'Extournée'. Et une nouvelle écriture apparaît dans la liste, préfixée EX, avec la description 'Extourne de...' suivie du numéro de l'originale — les deux sont donc explicitement liées. Cette écriture miroir est créée directement en statut Validée — le système la génère et la valide automatiquement, parce que c'est une opération technique réglementaire, pas une saisie manuelle. Les montants sont identiques mais débits et crédits sont inversés : l'effet net sur les soldes est exactement zéro. L'erreur est neutralisée, sans qu'on ait modifié un seul octet de l'écriture originale. C'est la piste d'audit parfaite : traçabilité totale, immuabilité garantie, conformité BCEAO assurée."

❓ Questions probables du jury — réponses courtes
Pourquoi deux microservices et pas un seul ?
"La séparation n'est pas cosmétique — elle est sécuritaire. Le service Reporting n'a physiquement accès à la base qu'en lecture, via un rôle PostgreSQL distinct. Si ce service est compromis, un attaquant ne peut pas modifier des écritures. C'est le principe du moindre privilège appliqué à l'architecture : chaque composant n'a que les droits strictement nécessaires à sa fonction."
La base de données est partagée — n'est-ce pas une faille ?
"C'est une limite que j'assume et que j'ai identifiée dans mon bilan. La solution idéale en microservices est une base par service, avec CDC — Change Data Capture — via Debezium ou similaire. Je l'ai mentionnée dans mes perspectives. Pour ce prototype, j'ai utilisé des rôles PostgreSQL différents pour restreindre les permissions, ce qui donne une isolation partielle acceptable dans un contexte académique."
Comment garantissez-vous que personne ne modifie la base directement, en dehors de l'API ?
"C'est effectivement la limite d'un système sans HSM. J'ai mis en place trois niveaux : les contraintes CHECK et les triggers PostgreSQL qui rejettent les modifications d'écritures POSTED même en SQL direct ; les rôles PostgreSQL qui limitent qui peut exécuter des UPDATE/DELETE ; et la journalisation de toutes les connexions à la base. Dans un système en production, on ajouterait un module de surveillance des accès directs à la base — une SIEM — et on chiffrerait les données au repos."
Pourquoi Kafka ? Une simple file de messages ne suffisait pas ?
"Kafka offre trois propriétés qu'une simple queue ne garantit pas : la persistance des messages sur disque, l'idempotence — on peut rejouer le même événement sans créer de doublon grâce au champ idempotency_key — et la capacité à rejouer l'historique complet si le service Reporting tombe et revient. C'est particulièrement important en comptabilité : on ne peut pas se permettre de perdre un événement, même si le consommateur est momentanément indisponible."
Comment avez-vous validé que le système est sécurisé ?
"Sur plusieurs axes. D'abord les tests automatisés : 128 tests pytest couvrent les cas nominaux et les cas d'échec — chaque règle RBAC, chaque contrainte métier. Le CI GitHub Actions les exécute à chaque commit. Ensuite les tests de charge k6 : j'ai simulé 100 utilisateurs simultanés pendant 5 minutes et atteint 71 requêtes par seconde avec un taux d'erreur de 3,7%, dont la majorité sont des erreurs 422 intentionnelles des tests de validation. Et enfin l'analyse de menaces avec le modèle STRIDE qui a guidé mes choix d'architecture depuis le début."
Quelle est la prochaine étape si ce système devait aller en production ?
"Trois chantiers prioritaires : premièrement, le passage à mTLS pour les communications inter-services — là, Kafka n'est pas chiffré entre services. Deuxièmement, la séparation des bases de données avec réplication unidirectionnelle vers le Reporting. Et troisièmement, une couche HSM pour la gestion des clés JWT — actuellement la clé est une variable d'environnement, ce qui est suffisant pour un prototype mais pas pour la production."
